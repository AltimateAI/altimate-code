- [L-fefb] Fact models in marts are named `fct_<verb_noun>` and dimensions `dim_<entity>`; a mart table without one of those prefixes does not ship, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-3bc9] Every `fct_` model states its grain in the YAML description as `Grain: one row per ...`, and a unique test on the surrogate key backs it, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-997e] Mart models expected to exceed 50M rows are materialized `incremental` with a `unique_key` and a 3-day lookback so late-arriving rows are picked up. <!-- h:0 x:0 -->
- [L-2fe6] In staging models, integer columns ending in `_cents` must be converted using the `{{ cents_to_dollars(...) }}` macro and renamed without the `_cents` suffix; no `*_cents` columns should pass through to staging output. <!-- h:3 x:0 -->
- [L-c420] Mart folders set `+materialized: table` once in `dbt_project.yml`, and mart models do not repeat it in their own config blocks, so project-level configuration changes are easy to find and review in isolation. <!-- h:0 x:0 -->
- [L-e76c] Marts read upstream models through `ref()` only; if a mart needs a new upstream field, add it to the intermediate layer first, then select it, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-3a7c] Dimension models carry `valid_from` and `valid_to` only when built from a snapshot; a plain dimension must not fake history columns, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-72a3] Net revenue is defined once under `models/marts/finance/` and reused; do not recompute it inside a downstream mart or BI model, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-78c4] Wide denormalized dashboard tables are named `rpt_<dashboard>` and are never joined back into other marts, because downstream dashboards and finance reconciliations depend on a predictable mart layer. <!-- h:0 x:0 -->
- [L-8536] If a source table has a soft-delete flag (e.g. `_is_deleted`), filter it out with `where not _is_deleted` in the renamed CTE and exclude that column from the select list; staging models must not expose soft-delete flags as output columns. <!-- h:2 x:0 -->
- [L-0c7d] Use the `timestamp` snapshot strategy when the source has a trustworthy `updated_at`; fall back to `check` only when it does not, since a mistake here silently corrupts history that cannot be rebuilt from the source. <!-- h:0 x:0 -->
- [L-6015] Snapshots write to the `snapshots` schema and the file name equals the snapshot name, one snapshot per file, since a mistake here silently corrupts history that cannot be rebuilt from the source. <!-- h:0 x:0 -->
- [L-2175] Snapshots select from a stable model via `ref()`, never from a view whose row set changes between runs, since a mistake here silently corrupts history that cannot be rebuilt from the source. <!-- h:0 x:0 -->
- [L-1f73] Dashboard exposures live in `models/marts/_exposures.yml`, each with an owner email and a `maturity` of high, medium or low, so the model layers stay predictable for every analyst who navigates the project. <!-- h:0 x:0 -->
- [L-d19c] Run `dbt snapshot` before `dbt run` in the nightly job, and never run snapshots in PR CI builds, since a mistake here silently corrupts history that cannot be rebuilt from the source. <!-- h:0 x:0 -->
- [L-8201] In staging models, every timestamp column must be wrapped with the `{{ to_utc('col') }}` macro and aliased with the `_at` suffix; bare timestamp aliases without the macro are not permitted. <!-- h:2 x:0 -->
- [L-382f] Set `invalidate_hard_deletes: true` on snapshots of tables whose source physically deletes rows, since a mistake here silently corrupts history that cannot be rebuilt from the source. <!-- h:0 x:0 -->
- [L-7659] Renaming or dropping a snapshot column needs a migration note in the PR, because existing history rows keep the old shape. <!-- h:0 x:0 -->
- [L-71e1] Seeds are for small static lookups under 1,000 rows; anything larger lands through the loader, not a CSV in git, because seed changes are reviewed as data changes and are expensive to unwind once deployed. <!-- h:0 x:0 -->
- [L-bf3f] Lookup seeds declare `+column_types` explicitly in the seeds YAML so a CSV edit cannot silently change a column's type. <!-- h:0 x:0 -->
- [L-8838] Seed CSVs never contain customer PII, even in sample or test rows, because seed changes are reviewed as data changes and are expensive to unwind once deployed. <!-- h:0 x:0 -->
- [L-0fd1] Lookup seeds are named `ref_<topic>` and keep one code per row with its human label alongside, because seed changes are reviewed as data changes and are expensive to unwind once deployed. <!-- h:0 x:0 -->
- [L-8aba] When adding a new source to a staging layer, also register it in the corresponding sources YAML file and ensure the model YAML lists only the columns that appear in the final select, using the aliased output names. <!-- h:0 x:0 -->
- [L-30c0] Intermediate models are prefixed `int_`, live in `models/intermediate/`, and are never granted to BI roles, so the model layers stay predictable for every analyst who navigates the project. <!-- h:0 x:0 -->
- [L-909e] Country and currency codes in lookup seeds use uppercase ISO 3166 and ISO 4217 values, because seed changes are reviewed as data changes and are expensive to unwind once deployed. <!-- h:0 x:0 -->
